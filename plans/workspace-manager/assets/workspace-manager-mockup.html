Where workspace management should live

Today the switcher only switches: it lists recent folders and offers “Open folder”, “Create workspace” (Android) and “Import from Git”. Everything below is about where remove / delete / reveal should go — and what a good launcher looks like.

Option A — row actions in the switcher

Smallest diff · stays inside role="menu"

The existing dropdown gains a trailing ⋯ and × on hover. Lowest code cost — no new surface. But nested buttons inside role="menu" rows are invalid for keyboard and screen readers, hover-reveal has no answer on touch, and a destructive action sits one mis-tap away from a quick switcher.

For comparison — Workspaces as a tab

Rejected · cross-workspace UI inside one workspace’s tab

The same list inside an editor tab works mechanically, but each window is one workspace — a cross-workspace launcher inside a workspace’s tab is conceptually odd, and dragging tabs out into windows is a separate large epic (cross-window tab state, per-workspace persistence, per-OS drop targets). Not recommended for this.

Behaviour notes

  • Remove = forget from recents only. Needs a new targeted forgetWorkspacePath desktop-state update — Rust merges recents today, so removing one entry can’t be expressed as a full-list write.
  • Delete = Android managed vaults only. Also wipes the hash-keyed metadata: settings/workspace-<hash>.json, search index, sync/workspace-<hash>.git, backups/workspace-<hash>/.
  • The workspace open in this window can’t be deleted or removed — close it first. One open in another window gets Focus.
  • Missing folders are flagged, not auto-removed — the path may be an unmounted drive or a renamed parent.
  • The modal doubles as the launcher when no workspace is open — same list, no editor dimmed behind the scrim.
