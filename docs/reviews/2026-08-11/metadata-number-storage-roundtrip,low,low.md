- name: Preserve float-vs-int distinction and guard against scientific-notation round-trip failure in number metadata storage
- file: /media/adam/extex/projects/thinkbrain-notes/apps/desktop/src-tauri/src/commands/search/metadata.rs
- lines: 178-185 (storage_parts), 187-207 (metadata_value_from_storage)
- description: `MetadataValue::storage_parts` serializes numbers via `value.to_string()` (line 183), and `metadata_value_from_storage` reads them back via `Number::from_str(value_text)` (line 193). Two issues arise from this text round-trip: (1) **Float-to-int flattening** — a frontmatter value like `rating: 3.0` arrives as `Number::from_f64(3.0)`, stores as the text `"3"`, and is read back as `Number` (i64 3). When serialized to the frontend via `MetadataValue::Number`'s untagged serde enum, this emits JSON `3` instead of `3.0`. The frontend type `NativeMetadataValue = string | number` (apps/desktop/src/native/commands.ts:358) accepts both, so functionally it still works, and predicate matching still works because a predicate `number(3.0)` also flattens to `"3"` for its `storage_parts` comparison. But the facet display value changes from `3.0` to `3`, which is a silent semantic shift for a user who authored `3.0`. The test `queries_scope_paths_keys_values_and_flattened_types` (metadata_tests.rs:174) asserts `number(3.0)` equality, which passes only because `serde_json::Number::PartialEq` compares numeric values across the i64/f64 representations — it does not verify the serialized JSON shape. (2) **Scientific-notation edge case** — `serde_json::Number::to_string()` on an f64 uses Rust's `Display`, which produces scientific notation for very large or very small magnitudes (e.g. `"1e20"`, `"1.5e-10"`). `Number::from_str` in `metadata_value_from_storage` would then attempt to parse that string; if serde_json's `Number::from_str` rejects scientific notation (it is stricter than full JSON number parsing in some versions), the row would trigger `FromSqlConversionFailure` and the entire `query_metadata` call would fail loudly. This is a low-probability path for note metadata but would be a runtime crash, not a silent issue. Fix: either (a) store numbers with a `value_subtype` discriminator (`'int'` vs `'float'`) and serialize floats with `format!("{:?}", f64)` or preserve the original JSON token, or (b) at minimum, use `value.to_string()` for storage but verify `Number::from_str` round-trips for all f64 magnitudes and add a test with `1e20` / `1e-10` to lock the contract. For the int/float display issue, consider serializing `MetadataValue::Number` via a custom serde serializer that always emits an f64 when the original was f64.
- resolution: Rejected. The frontend contract is a JavaScript `number`, which has no integer-versus-float lexical subtype, so `3` and `3.0` are the same supported value rather than a lost distinction. `serde_json::Number` accepts valid JSON exponent notation; storage and predicate values use the same canonical conversion.
- verification: Read metadata.rs:178-185 (storage_parts uses to_string), metadata.rs:187-207 (from_str round-trip), metadata_tests.rs:41-43 (number() helper uses from_f64), metadata_tests.rs:170-176 (asserts number(3.0) equality but not JSON shape), and apps/desktop/src/native/commands.ts:358 (NativeMetadataValue = string | number accepts both int and float).
