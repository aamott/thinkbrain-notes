- description: Two numeric edge cases in the change handler:
  1. Clearing the input fires `onChange` with `0`. `Number("")` evaluates to `0` (not `NaN`), so the guard `if (!Number.isNaN(parsed))` (line 30) passes and `onChange(0)` is called. This stages a `0` for the setting even though the user intended to clear/empty the field. For a setting with a non-zero default or min, this silently writes a wrong value into staged changes. The displayed value (line 23) shows `""` when `numericValue` is `NaN`, but a freshly-cleared field produces `parsed = 0`, so the next render shows `0` instead of staying empty.
  2. `min`/`max` from the definition are applied as HTML attributes (lines 24-25) but the change handler does not clamp `parsed` to `[min, max]`. The browser's native number input does not enforce `min`/`max` on typed input (only on spinner/step), so a user can type a value below `min` or above `max` and it will be staged. The registry's built-in validation may catch it on save, but the control should either clamp or skip staging out-of-range values to avoid surfacing a validation error after the fact.
  Suggested fix: when `e.target.value === ""`, skip the `onChange` call (treat as "no change yet") or stage `undefined`/`null` per the store's contract; and clamp `parsed` to `[definition.min ?? -Infinity, definition.max ?? Infinity]` before calling `onChange`.
