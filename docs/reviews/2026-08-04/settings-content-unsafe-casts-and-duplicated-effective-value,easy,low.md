- description: Two maintainability/type-safety issues:
  1. `searchSections` (lines 60-75) types its `sections` parameter as `readonly { id: string; label: string; subsections?: readonly unknown[] }[]` and recurses by casting `section.subsections as readonly { id; label; subsections?: readonly unknown[] }[]` (line 68). The actual data is `SettingSection` (packages/core/src/settings/types.ts lines 61-66), which already types `subsections` as `readonly SettingSection[]`. The hand-rolled structural type and `unknown[]` cast defeat type safety: if `SettingSection` gains a required field, this code will not error. It should accept `readonly SettingSection[]` directly (the same type `SettingsNav.findSectionLabel` already uses at line 156).
  2. `computeEffectiveValue` (lines 32-43) reimplements the resolution order documented on `SettingsStoreState.getEffectiveValue` (settingsStore.ts lines 452-460). The two implementations differ in their default source: the inline version takes `defaultValue` as a parameter (supplied as `definition.default` at the call site, line 224), while the store action looks up `appSettingsRegistry.getDefinition(key)?.default` (line 459). For a registered key these are the same value, but they are now two sources of truth — if the store's resolution order changes (e.g. workspace overrides app, or a new "inherited" layer is added), the inline copy in SettingsContent will silently drift and render a different value than `getEffectiveValue` would return to other consumers. The file's own header comment (lines 9-13) acknowledges this duplication and justifies it on reactivity grounds, but the reactivity concern could be addressed by selecting the raw maps (already done) and calling `getEffectiveValue` from a `useSettingsStore.getState()` snapshot inside the render, eliminating the duplicated logic.
