- description: The current `attach` bootstraps inside the lock, so two concurrent `attach` calls for the same `key` serialize: the first inserts its engine, the second sees `contains_key` is true (line 58) and skips bootstrapping. Safe.

  However, the scalability fix (moving `bootstrap` outside the lock — see "attach bootstraps the workspace while holding the global registry lock") introduces a race: two windows opening the same workspace concurrently can both pass the `contains_key` check, both bootstrap, and both attempt to insert. `HashMap::insert` returns the old value, but the code on line 62-64 ignores it — the second insert silently overwrites the first `Arc<Engine>`. If the first engine had accumulated pending changes (unlikely in the first-open case, but possible if the windows open milliseconds apart and the watcher fires between the first insert and the second), those pending edits are dropped when the first `Arc` is released.

  The fix is the double-check described in the bootstrap-under-lock finding: after re-acquiring the lock, re-check `contains_key`; if an engine now exists, use it and drop the newly-created one. This must be implemented *together with* the lock-release fix — doing one without the other either reintroduces the scalability problem or introduces this race.

  Even in the *current* (locked-bootstrap) code, there's a subtler variant: `bootstrap` for a `HasOwnGit` vault returns `Ok(false)` early (line 60) without inserting an engine, but `interest.acquire(key, label)` (line 69) still runs. So `interest` tracks a key with no engine. A subsequent `detach` (line 81) calls `interest.release` which returns true on last release, then `engines.remove(key)` is a no-op (no engine was inserted). Harmless. But it means `interest.is_watched(key)` returns true for a `HasOwnGit` vault, which could mislead a future caller. Worth a comment or skipping `acquire` for `HasOwnGit`.
- verification: Read of `attach` (49-75); traced the `contains_key` → bootstrap → insert sequence. The `HasOwnGit` interest leak is on line 60 (early return) vs line 69 (unconditional acquire).
