- description: `MarkdownFileEntry` (markdown.rs:14-21) has fields `relative_path`, `file_name`, `parent_path`, `byte_size`, `updated_at` — exactly the subset of `WorkspaceEntry` (workspace.rs:87-96) where `kind == "file"` and `is_markdown == true`. The constructor `markdown_file_entry` (markdown.rs:354-392) is a line-for-line parallel of `workspace_entry` (workspace.rs:610-650) for the file-only case: same `strip_prefix` + `replace('\\','/')`, same `fs::metadata`, same `modified().duration_since(UNIX_EPOCH).as_millis() as u64` for `updated_at`, same `file_name().unwrap_or(relative_path.clone())` and `parent_path` computation. The only difference is `WorkspaceEntry` adds `kind`, `is_markdown`, and `is_dir`-gated `byte_size`.

  `list_markdown_files` (markdown.rs:31-36) returns `Vec<MarkdownFileEntry>` and is registered as a Tauri command (mod.rs:46). `open_workspace` returns `WorkspaceSnapshot { files: Vec<MarkdownFileEntry> }` (workspace.rs:76-79). So `MarkdownFileEntry` is a separate IPC return type, not just an internal helper — it cannot be silently replaced with `WorkspaceEntry` without a frontend change. That makes this a *medium* win, not a quick one: collapsing the two would change the IPC shape (`WorkspaceEntry` has extra fields `kind`, `is_markdown`) and require the frontend `native/commands.ts` + `workspaceAdapter.ts` to filter on `is_markdown`.

  Recommended path: keep `MarkdownFileEntry` as the IPC type but have `markdown_file_entry` delegate to `workspace_entry` and project out the five fields, OR extract the shared `relative_path`/`parent_path`/`updated_at` computation into a small `fn entry_metadata(root, path) -> (relative_path, parent_path, file_name, byte_size, updated_at)` helper used by both. The latter is the smaller change and removes the real duplication (the metadata-reading block) without touching IPC.
