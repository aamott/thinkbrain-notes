- name: `SystemGitRunner::run` spawns a thread per command and abandons it on timeout — child process leaks
- file: /media/adam/extex/projects/thinkbrain-notes/apps/desktop/src-tauri/src/commands/git.rs
- lines: 169-187
- description: `SystemGitRunner::run` spawns `git` via `command.spawn()`, then spawns a *second* std thread to call `child.wait_with_output()` and sends the result over an `mpsc::channel`. The outer call does `rx.recv_timeout(GIT_COMMAND_TIMEOUT)` (5s). On timeout it returns `GitRunError::TimedOut` and drops `rx` — but the spawned thread is still blocked in `wait_with_output()`, which is still blocked waiting for the `git` child to exit. Neither the thread nor the `git` child is killed. A `git` invocation that hangs (e.g. waiting on a credential prompt despite `GIT_TERMINAL_PROMPT=0`, or a slow large-repo operation) will leave a zombie `git` process and a parked thread per timeout, for the lifetime of the app. Repeated timeouts accumulate.

  The thread-per-call is also wasteful for the common case: `wait_with_output()` is already a blocking call; the only reason for the helper thread is to apply a timeout, since `std::process::Child::wait` has no timeout API. A cleaner fix is to use `child.kill()` on timeout: keep the `Child` handle in the outer scope (don't move it into the thread), have the thread send `child.wait_with_output()`'s result, and on `recv_timeout` timeout, call `child.kill()` (and ideally `child.wait()` to reap). That requires restructuring so the `Child` is not moved into the thread — e.g. the thread takes `child` by reference is not possible, so the simpler pattern is: thread owns `child`, outer scope sends a "kill" signal on timeout via a second channel, thread checks after `wait`. Or use the `wait-timeout` crate (~30 lines saved, correct behavior).

  This is a real resource leak, not theoretical: `GIT_TERMINAL_PROMPT=0` causes git to *fail* on missing credentials, not hang, but a `git fsck` or large `git status` over a network filesystem can exceed 5s.
