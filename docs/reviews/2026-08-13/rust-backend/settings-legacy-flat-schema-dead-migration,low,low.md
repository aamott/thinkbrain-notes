- description: Two legacy-schema accommodations appear to be unreachable in practice and add maintenance surface:
  1. `read_desktop_state` (lines 390-407) has a fallback that reads flat top-level keys `lastWorkspacePath` and `explorerOpen` from the app-settings root when no `desktopState` object exists. This was the pre-versioned schema. `DESKTOP_STATE_VERSION` is `5` (line 21), so the flat schema has not been written for at least 5 migrations. `update_desktop_state_contents` (lines 328-330) then *removes* those same flat keys (`app_settings.remove("lastWorkspacePath")`, `remove("explorerOpen")`) on every write — a migration that has run on every save since version 1. Any user who has opened the app once since v1 has already been migrated; the removal runs forever anyway.
  2. The fallback in `read_desktop_state` is only reached when `app_settings.get(DESKTOP_STATE_KEY)` is `None`, i.e. a settings file with no `desktopState` at all — which `parse_app_settings_record` produces from a missing or unparseable file, in which case `default_desktop_state()` is the correct answer and the legacy scan can only ever find keys that the very next write will delete.

  Recommend: drop the legacy-key scan in `read_desktop_state` (return `default_desktop_state()` directly when `desktopState` is absent) and drop the two `app_settings.remove(...)` calls in `update_desktop_state_contents`. If a migration is still desired, gate it on `DESKTOP_STATE_VERSION < 5` once, not on every write. Verify against `tests.rs` lines ~2344-2420 (the legacy-migration tests) before removing — if those tests exist to lock the migration, decide whether to keep them or delete with the code.
