- description: `EMPTY_WIKI_LINK_INDEX` (core lines 46-51) creates fresh `Map` instances at module load, so the *outer* references are safe. However, `removeNote` (core line 204) and `addNote` (core line 227) both start with `new Map(index.forward)` — which copies entries — so they do not mutate the empty index's maps. So this is **not** a bug; recording it because the store's initial state is `EMPTY_WIKI_LINK_INDEX` (line 93) and a careless future change to `addNote`/`removeNote` that mutated in place would corrupt the shared singleton.

  The actual concern is subtler: `removeDocument` (store lines 155-159) and `reindexRenamedDocument` (store lines 140-153) call `removeNote`/`addNote` and immediately `set({ wikiLinkIndex: next, ... })`. Because `addNote`/`removeNote` rebuild `backlinks`/`unresolved` via `buildReverseMaps` (core lines 109-128) on *every* single-note mutation, an incremental save in a 10k-note vault triggers an O(n) reverse-map rebuild (iterate every forward-link entry). This is the same cost as the search store's incremental upsert, but the search store delegates to a SQLite FTS5 `INSERT`; here the rebuild is in-memory JS over the whole forward map. For a vault with many notes this can make every keystroke-save visibly janky. The core module docstring (lines 98-108) explicitly justifies this ("Recomputing on each mutation keeps the logic simple and correct") — simplicity over performance, which is fine for small vaults but should be flagged for large ones.

- verification: Read `packages/core/src/wikiLinkIndex.ts` lines 46-51, 109-128, 200-246. Confirmed `addNote`/`removeNote` use `new Map(index.forward)` (copy) and `index.noteIndex.filter`/spread (copy), so the empty singleton is not mutated. Confirmed `buildReverseMaps` iterates the entire `forward` map on every call.
