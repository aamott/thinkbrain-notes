- description: The two index stores are wired into `DesktopShell` identically (shell lines 343-344 call both `indexWorkspace`, lines 352-353 call both `clearWorkspace`, lines 442 and 445 call both `subscribeToEvents`). They subscribe to the same four events. But their internal semantics diverge in ways that can produce inconsistent user-visible state:

  1. **Abort**: `searchIndexStore` aborts in-flight indexing on new `indexWorkspace` and on `clearWorkspace` (search lines 78, 114). `wikiLinkIndexStore` has no abort (wiki lines 97-127). After a rapid workspace switch, the search index may be `ready` for the new workspace while the wiki-link index is still reading files from the *old* workspace (the reads can't be cancelled). The backlinks panel and autocomplete will be empty/stale longer than the search panel.
  2. **Status surfacing**: `searchIndexStore` exposes a `status: SearchIndexStatus` discriminated union (`no-workspace | indexing | ready | error`) so UI can show progress. `wikiLinkIndexStore` exposes only `rootPath` and the index data — no `indexing`/`error` state. UI consumers cannot tell whether the wiki-link index is mid-rebuild or failed; they just see an empty `noteIndex`. A large vault will show "no backlinks" with no spinner.
  3. **Error handling**: `searchIndexStore.reindexDocument` (search lines 126-133) `console.error`s on failure. `wikiLinkIndexStore.reindexDocument` (wiki lines 129-138) silently returns on `null` from `readAndParse` (which only `console.warn`s). So a save failure logs at different severities in the two stores, and the wiki-link store has no error path at all.
  4. **`removeDocument` sync vs async**: `searchIndexStore.removeDocument` is `async` (search line 135) and awaits `searchService.removeDocument`. `wikiLinkIndexStore.removeDocument` is synchronous (wiki line 155). The event handler at wiki line 173 calls it without `void`/`await` while the search equivalent at search line 169 uses `void get().removeDocument(...)`. Functionally fine, but the asymmetry means a future refactor that makes wiki `removeDocument` async could silently drop the call (the `void` is missing at wiki line 173).

- verification: Read both stores in full and compared line-by-line. Confirmed `searchIndexStore` has `AbortController` + `status` + `console.error`; `wikiLinkIndexStore` has none of these. Confirmed `DesktopShell` wires them identically, so the divergence is internal and invisible to the shell.
