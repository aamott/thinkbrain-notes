- name: Autocomplete does not handle `[[|` (pipe with empty target), nested brackets, or cursor at start of document
- file: /media/adam/extex/projects/thinkbrain-notes/apps/desktop/src/tabs/wikiLinkAutocomplete.ts
- lines: 99-119
- description: The trigger regex `/\[\[[^\]|]*$/` (line 103) matches from `[[` to the cursor, stopping at `]` or `|`. Several edge cases are not handled or not tested:

  1. **`[[|alias]]`** (pipe immediately after brackets, empty target): `matchBefore` returns `[[` with `query = ""` (line 108), so the popup shows *all* notes. The user typed a pipe intending an alias-only completion, but gets every note. The regex `[^\]|]*` matches the empty string between `[[` and `|`, so `before.text === "[["` and the pipe is *after* the cursor — actually if the cursor is right after `[[|`, the regex `[^\]|]*$` fails to match because `|` is excluded, so `matchBefore` returns `null` and no popup shows. Good. But if the cursor is *between* `[[` and `|` (e.g. `[[|alias]]` with cursor at position 2), the regex matches `[[` and the popup shows all notes — surprising. Not tested.
  2. **Cursor at start of document** (`pos === 0`): `matchBefore` runs `from.exec("")` which returns `null`, so no popup. Correct, but not tested — `mockContext` always passes a non-empty `doc`.
  3. **Very long query** (e.g. `[[` + 500 chars): `buildCompletions` (lines 43-89) lowercases and `.includes()`-checks the needle against every note's filename/title/aliases. For a 500-char needle this is O(notes × fields) substring scans on a needle that almost certainly matches nothing. Cheap in practice but the empty-result path returns `null` (line 110) so the popup closes — fine. No test for a long query.
  4. **Special characters in query** (`[[note/with/slash`, `[[note"quote`, `[[note\n`): the regex `[^\]|]*` excludes `]` and `|` but allows `/`, `"`, newlines, etc. A `/` in the query is treated as a literal substring, so `[[fold` matches `folder/Other.md` only if `fold` is a substring of the basename `other` — it isn't, so no match. But `[[folder/oth` would match nothing because `baseName(note.fileName)` strips only the extension, leaving `Other`, and `folder/oth` is not a substring of `other`. So path-style queries silently fail even though `resolveWikiLinkTarget` (linkResolver.ts lines 113-120) *does* support relative-path matches. The autocomplete is inconsistent with the resolver: the resolver matches by full path, the autocomplete only matches by basename/title/alias. A user typing `[[folder/oth` gets no popup, but the link *would* resolve after completion. Not tested.
  5. **Newline inside `[[...`**: `matchBefore` slices `doc.slice(0, pos)` and runs the regex globally; `[^\]|]*$` matches across newlines (no `s` flag needed since `.` isn't used, and `[^\]|]` matches `\n`). So `[[foo\nbar` would match with `query = "foo\nbar"`. Probably unintended — wiki links don't span lines. Not tested.
  6. **Duplicate labels**: two notes with the same title produce two completions with the same `label` (line 68). CodeMirror's completion UI may collapse or confusingly display them. The `detail` (relativePath) disambiguates, but no test asserts behavior with duplicate labels.

- verification: Read `wikiLinkAutocomplete.ts` lines 43-119 and `wikiLinkAutocomplete.test.ts` lines 1-153. Confirmed no test covers pipe-at-cursor, start-of-doc, long queries, special characters, newlines, or duplicate labels. Cross-referenced `linkResolver.ts` lines 113-120 to confirm the resolver supports path matches that the autocomplete does not.
