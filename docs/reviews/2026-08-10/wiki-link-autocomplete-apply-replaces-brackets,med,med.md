- name: `apply: [[Target]]` replaces the opening brackets, breaking multi-cursor and partial-accept semantics
- file: /media/adam/extex/projects/thinkbrain-notes/apps/desktop/src/tabs/wikiLinkAutocomplete.ts
- lines: 66-117
- description: Each completion sets `apply: \`[[${target}]]\`` (line 72) and the result sets `from: before.from, to: context.pos` (lines 113-114). `before.from` points at the first `[` (per the regex `/\[\[[^\]|]*$/`), so accepting a completion replaces `[[partial` with `[[Target]]` — including the opening brackets. This works for the common case but has two issues:

  1. **CodeMirror `apply` as a string** replaces the `from`–`to` range with the literal string. Because `from` is the first `[` and the string starts with `[[`, the brackets are written twice if CodeMirror ever calls `apply` with a different range (it shouldn't, but the contract is that `apply` is the *full* replacement text for the `from`/`to` range). The current code is correct, but using a string `apply` instead of an `{from, to, insert}` object or a function makes the assumption implicit. If a future change alters `from`/`to` (e.g. to only replace the partial text after `[[`), the string `apply` would produce `[[[[Target]]`.
  2. **Partial acceptance / `activateOnTyping`**: with `activateOnTyping: true` (line 140), CodeMirror re-queries the source as the user types. `validFor: /^\[\[[^\]|]*$/` (line 116) keeps the popup alive while typing inside the brackets. But once a completion is accepted, the cursor lands after `]]`. If the user then backspaces into `[[Target|` to add an alias, the regex excludes `|` so the popup closes — correct. However, if the user accepts a completion and *keeps typing* (e.g. `[[Target]] more text`), the popup correctly closes. No bug, but the interaction is untested.

  More substantively: the `apply` string always uses `baseName(note.fileName)` as the target (line 66), discarding the user's typed path prefix. If the user types `[[folder/oth` and a completion for `folder/Other.md` existed (it doesn't, per the path-match gap in the other finding), accepting it would insert `[[Other]]` — losing the `folder/` prefix. This is inconsistent with Obsidian, which preserves the typed path style. Even for basename matches, if two notes have the same basename in different folders, the `apply` produces an ambiguous `[[Other]]` that may resolve to the wrong note.

- verification: Read `wikiLinkAutocomplete.ts` lines 66-117. Confirmed `apply` is a string literal `[[${target}]]` with `target = baseName(note.fileName)`, and `from`/`to` span the brackets. No test asserts the multi-cursor or duplicate-basename scenario.
