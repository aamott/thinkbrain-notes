- description: The data flow is: `note.saved` event → `subscribeToEvents` listener (store line 163) → `reindexDocument` → `set({ noteIndex: next.noteIndex })` (store line 137) → Zustand notifies subscribers → `DesktopShell` selector `useWikiLinkIndexStore((s) => s.noteIndex)` (shell line 99) re-renders → `noteIndex` prop flows to `MarkdownEditor` → `wikiLinkAutocompleteCompartment.reconfigure(wikiLinkAutocomplete(noteIndex))` → new closure inside `wikiLinkCompletionSource(notes)`.

  This chain has several points where staleness can leak:
  1. **`noteIndex` identity**: `addNote`/`removeNote` (core) always return a *new* `noteIndex` array (spread or filter), so the Zustand selector at shell line 99 will see a new reference and re-render. Good. But if a future core change mutated `noteIndex` in place, the selector would not fire (Zustand uses `Object.is` by default). No test asserts that `addNote`/`removeNote` return a fresh array reference.
  2. **Reconfigure must actually happen**: the chain depends on `MarkdownEditor` calling `reconfigure` in a `useEffect` keyed on `noteIndex`. If that effect is missing or has a stale closure, the autocomplete keeps the old `notes` array. The autocomplete module itself has no way to detect this — it just serves whatever `notes` it closed over.
  3. **Two open editors**: `markdownEditorHooks.ts` lines 101-109 wires the compartment per-editor. Each editor must independently reconfigure. If `DesktopShell` passes `noteIndex` to one editor but not another (e.g. a popout window), the popout's autocomplete is stale. The `noteIndex` is selected once at the shell level (line 99) and threaded via props, so any editor mounted without that prop defaults to `?? []` (hooks line 106) and gets no autocomplete — silent failure.
  4. **Event vs. render timing**: `subscribeToEvents` fires `reindexDocument` asynchronously (`void get().reindexDocument(...)` at store line 164). The `set` happens after the awaited `readAndParse`. Between the `note.saved` event and the `set`, the autocomplete still shows the old index. If the user is mid-completion in another editor when a save happens elsewhere, the popup doesn't update until the read completes and React re-renders. Probably acceptable, but untested.
